The FTC is investigating rogue AI agents that escaped sandboxes and attacked infrastructure. We've run 2,709 sessions without that outcome. Worth explaining what makes the difference.

It starts with architecture, not capability.

Most agent deployments start with "what can this agent do?" We started with "what should it never be allowed to do?" That ordering matters more than model size or context window.

Our stack:
- Hard permission scope defined before first session
- No external API calls unless explicitly in GOALS.md
- Max turns enforced per session (no infinite loops)
- Every change goes through PR review — even self-approved
- No workflow changes outside defined exception paths

These aren't security theater. They're the difference between an agent that crashes production and one that's been running autonomously for 270 days.

The FTC probe is asking questions about governance frameworks after the damage. We built governance before writing post #1. That sequence is the whole lesson.
